# スロット用環境変数マージ

## 1. 概要

プロジェクトの .env / .envrc（dotenv / direnv）と、スロットごとの環境変数をマージして利用できるようにする。ベースの .env は変更せず、スロット用の値を上乗せ・上書きする。

## 2. 前提条件

- プロジェクトに **.env** または **.envrc**（あるいは両方）が存在する。
- dotenv または direnv により読み込まれる想定。
- **.env はプロジェクト管理下で Git 追跡対象**とする。git-slot は .env を編集しない。

## 3. 要件

### 3.1 スロット用の環境変数

- 少なくとも **スロット名**（例: `GSL_SLOT_NAME`）をスロットごとに環境変数として持てるようにする。
- 任意で、**スロットごとの key-value**（例: `PORT=3001`, `APP_ENV=slot-dev`）を設定できるようにする。

### 3.2 設定の置き場所

- **git-slot の設定**（例: `git-slot.toml`）でスロットごとの env を指定できるようにする。
- または **.env.slot** 等のファイル**をスロット用の定義として扱える**ようにする（ファイル名・形式は要検討）。

### 3.3 マージの挙動

- 最終的に **.env（および .envrc）とスロット用の環境変数がマージされた形**で読み込まれる。
- **同一キーが両方に定義されている場合は、スロット用の値が優先する**（後勝ち）。

## 4. 受け入れ条件（案）

| ID | 内容 |
|----|------|
| AC-SENV-001 | .env は Git 追跡対象のまま変更しない |
| AC-SENV-002 | スロット名（少なくとも GSL_SLOT_NAME）がスロットごとに設定される |
| AC-SENV-003 | スロットごとの追加 key-value を設定できる（設定ファイルまたは .env.slot 等） |
| AC-SENV-004 | 読み込み時は .env / .envrc とスロット用がマージされ、同一キーはスロット用が優先する |

## 5. 設計上の注意（メモ）

- **アプリに git-slot 依存を入れない**: マージは direnv の `source_env` や、git-slot が生成する「スロット用のみのファイル」を既存の .envrc から 1 行で読む形にするなど、プロジェクト側の変更を最小にする。
- **定義の永続化**: スロット用の定義はスロット配下ではなく、リポジトリルートや git-slot 設定に置き、load 時にスロット配下へ「マージ結果」または「スロット用レイヤーだけ」を生成する方式が clear と相性が良い。
- **.env.slot の扱い**: 「.env.slot を読む」をアプリに書かせるとプロジェクトが git-slot に依存するため、direnv や git-slot が生成するファイルを source する方式を優先する。

## 6. 解決案（複数案）

以下、要件を満たしうる解決案を列挙する。併用や組み合わせも可能。

---

### 案 A: direnv で「スロット用のみ」を後から読む（生成ファイル）

- **やること**: load 時にスロット配下に **.envrc.slot**（または .env.slot）を生成する。中身は `export GSL_SLOT_NAME=...` と、設定で指定した key-value のみ。
- **プロジェクト側**: .envrc の末尾に 1 行だけ追加する（例: `source_env_if_exists .envrc.slot`）。.env は触らない。
- **マージ**: direnv が .envrc を評価（その中で `dotenv` で .env を読む）→ 続けて .envrc.slot を source → 同一キーは後勝ち。
- **長所**: アプリは変更不要。.env は触らない。定義は git-slot 設定（と GSL_*）に集約できる。
- **短所**: direnv 必須。.envrc に 1 行入れる必要がある（追跡するかはプロジェクト次第）。

---

### 案 B: マージ済みファイルを 1 本だけスロットに生成（direnv が読む）

- **やること**: load 時に、**.env の内容とスロット用をマージした結果**を 1 ファイル（例: **.env.local** または **.env.merged**）に書き、スロット配下に置く。同一キーはスロット用が優先。
- **プロジェクト側**: .envrc で「.env を読む → あれば .env.local を読む（上書き）」のようにする（例: `dotenv` のあと `dotenv_if_exists .env.local`）。ルートの .env は触らない。
- **マージ**: git-slot が「リポジトリの .env 相当の内容」とスロット用をマージして .env.local を生成。direnv は .env と .env.local の両方を読む（または .env.local だけ読むなら、その中にマージ結果が全部入っている）。
- **長所**: マージ処理が git-slot 側に閉じる。direnv の設定は「.env の次に .env.local」の 1 パターンでよい。
- **短所**: リポジトリの .env を git-slot が読む必要がある（worktree のルートかメイン worktree の .env を参照）。direnv 必須。

---

### 案 C: 設定は git-slot.toml のみ。スロット用レイヤーだけ生成

- **やること**: スロットごとの key-value は **git-slot.toml の `[[slots]]` に `env = { PORT = "3001" }` のように書く**。load 時に GSL_* とこの env を .envrc.slot（または .env.slot）に書き出す。
- **プロジェクト側**: 案 A と同様、.envrc で `source_env_if_exists .envrc.slot`。
- **長所**: 定義が 1 か所（git-slot.toml）。.env.slot のような別ファイルをユーザーが持たなくてよい。
- **短所**: スロットごとの設定を変えるたびに toml を編集する必要がある。direnv 必須。

---

### 案 D: リポジトリに .env.slot または .env.slot.<slotname> を置く（オプション）

- **やること**: スロット用の定義を **リポジトリ側のファイル**（.env.slot または .env.slot.main-work など）で持てるようにする。load 時にその内容をスロット配下にコピーするか、direnv が読むファイルとして使う。
- **マージ**: .env は既存どおり。.env.slot（または slot 名対応のファイル）を direnv や dotenv で「後から読む」ようにすれば後勝ち。
- **長所**: スロットごとの値をファイルで管理したい場合に自然。Git で追跡するか ignore するか選べる。
- **短所**: ファイル名規則と「どのスロットにどのファイルを対応させるか」のルールが必要。direnv またはアプリの読み順の設定が必要。

---

### 案 E: git slot exec でだけ env を注入（ファイルに頼らない）

- **実装状況**: **`git slot exec`** および **`git slot which`** として実装済み。スロット省略時は `which` と同じく `git rev-parse --show-toplevel` でスロットを決定する。
- **やること**: **`git slot exec <slot> -- <cmd>`** のように、git-slot が子プロセスを起動するときに、GSL_* と設定の env を `cmd.Env` で渡す。マージは「既存の .env はアプリが読む + プロセスには git-slot が渡した env が上乗せ」で、OS の env の後勝ちで実現。対話シェル用の `GSL_SHELL_SESSION` は `exec` の子には付けない（`git slot shell` との区別）。
- **プロジェクト側**: 変更不要。.env はアプリが従来どおり読む。スロットで動かすときだけ `git slot exec` を使う。
- **長所**: direnv 不要。.envrc を触らない。プロジェクトが git-slot に依存しない。
- **短所**: 「cd してから npm start」では効かない。必ず `git slot exec` 経由で起動する必要がある。

---

### 案 F: ハイブリッド（設定 toml + オプションで .env.slot ファイル）

- **やること**: 基本は案 C（git-slot.toml の `[[slots]] env`）。加えて、**リポジトリに .env.slot や .env.slot.<name> があれば、その内容もマージ**する。load 時に GSL_* + toml の env + ファイルの内容を合わせて 1 つのスロット用レイヤーを生成し、.envrc.slot に書き出す。
- **マージ**: .envrc で .env → .envrc.slot の順で読む（案 A 同様）。
- **長所**: 定型は toml、個別の大量設定はファイルで、と使い分けできる。
- **短所**: 実装と優先順（toml とファイルのどちらが上か）のルールが必要。

---

### 案 G: dotenv のみのプロジェクト（direnv なし）で「後から読む」をアプリに任せる

- **やること**: git-slot は load 時に **.env.slot** をスロット配下に生成するだけ。アプリの起動コードで「.env を読んだあと .env.slot を読む（override）」を追加する。
- **長所**: direnv がなくても動く。
- **短所**: アプリが git-slot の慣習（.env.slot）に依存する。プロジェクトのポータビリティが下がる。要件「アプリに依存させない」と相反する可能性あり。

---

### 比較の目安

| 案 | direnv | .env 変更 | アプリ変更 | 定義の置き場所 |
|----|--------|-----------|------------|----------------|
| A  | 必須   | 不要(.envrc に 1 行) | 不要 | git-slot 設定 |
| B  | 必須   | 不要     | 不要 | git-slot が .env を読んでマージ |
| C  | 必須   | 不要     | 不要 | git-slot.toml のみ |
| D  | 推奨   | 不要     | 不要 | リポジトリの .env.slot 等 |
| E  | 不要   | 不要     | 不要 | git-slot 設定（exec 時のみ） |
| F  | 必須   | 不要     | 不要 | toml + オプションでファイル |
| G  | 不要   | 不要     | **必要** | git-slot が生成する .env.slot |

## 7. 詳細解説（誰が .env / .envrc を読むか）

### 7.1 direnv の入口は常に `.envrc` だけ

direnv は、ディレクトリに入ったとき **`.envrc` を評価する**のが基本動作である。**`.env` は自動では読まれない**。多くのプロジェクトでは `.envrc` の中に **`dotenv`**（または `use dotenv`）と書いてあり、それが「カレントディレクトリの `.env` を読んで環境変数に載せる」指定になっている。

したがって、

- **「.env も読みたい」** → すでにプロジェクトの `.envrc` に `dotenv` 等が書いてある前提で、その **続き**でスロット用レイヤーを読む必要がある。
- **案 A / C / D / F** で書いた「.envrc に 1 行追加」は、まさにこの **第 2 段（スロット用を後から読む）** を足すためのものである。第 1 段（.env を読む）は **もともとプロジェクトの .envrc が担当**している。

### 7.2 案 B / C / D それぞれの「読み方」

| 案 | `.env` を誰が読むか | スロット用を誰が読むか | プロジェクト側で必要なこと |
|----|---------------------|-------------------------|---------------------------|
| **B** | 従来どおり `.envrc` の `dotenv`（または同等） | `.envrc` が **`dotenv_if_exists .env.local`** のように **2 本目のファイル**を読む | `.envrc` に **2 本目を読む行**が必要（`.env` 用の `dotenv` は既存想定） |
| **C** | 同上 | `.envrc` が **`source_env_if_exists .envrc.slot`** 等で、git-slot が生成した **export だけのファイル**を source | `.envrc` に **source 用の 1 行**が必要 |
| **D** | 同上 | `.envrc` が `.env.slot` を `dotenv_if_exists` するか、`.envrc.slot` を source するか | **スロット用ファイルを読む行**が `.envrc` に必要（ファイル名は規約で決める） |

いずれも **「マージされた結果をプロセスの環境変数に載せる」** のは direnv の評価結果であり、そのための **レシピは `.envrc` に書かれている**必要がある。案 B は「2 段 dotenv」、案 C/D は「dotenv のあと source またはもう 1 回 dotenv」という違いだけである。

### 7.3 `.envrc` を一切変更できない場合

- 案 **A / B / C / D / F**（従来の説明どおり）は、**スロット用レイヤーを direnv に読ませる**ために、**何らかのフックが `.envrc` に存在する必要がある**。
- プロジェクトの `.envrc` が **最初から**「存在すれば `.env.local` や `.envrc.slot` を読む」ような行を含んでいるなら、git-slot は **ファイル生成だけ**でよく、**追記は不要**。逆に、**そうした行が無い .envrc を変更してはいけない**制約があるなら、**direnv 経由のマージ案は成立しない**。
- その場合、**アプリ変更なし・.env 変更なし・.envrc 変更なし**を同時に満たすのは、実質 **案 E（`git slot exec` で子プロセスに env を渡す）** か、**IDE/ターミナルが起動時に別手段で env を注入する**など、別経路になる。

### 7.4 案 E（exec）について

- **起動コマンドは変わる**。`npm start` ではなく **`git slot exec <slot> -- npm start`** のように、git-slot が **子プロセスを起動する経路**に乗せる必要がある。
- マージのイメージ: アプリが起動時に `.env` を読むと、ファイル由来の変数が `process.env` に入る。一方、親プロセス（git-slot）が **すでに `GSL_*` やスロット用の key-value を OS の環境変数として子に渡している**場合、多くのランタイムでは **既に設定されている環境変数が `.env` のデフォルトより優先**される、または **`.env` が先で OS の env が上書きしない**など挙動がライブラリ依存になる。**「スロットが必ず勝つ」**を厳密に担保するなら、exec 時に渡す env とアプリの dotenv の **読み順・override 規則**をドキュメントで明示する必要がある。

### 7.5 案 F の仕組み

- **入力が 2 系統**: (1) `git-slot.toml` の `[[slots]] env`、(2) 任意でリポジトリにある `.env.slot` / `.env.slot.<slotname>` などのファイル。
- **load 時に git-slot が** これらを **規則どおりにマージ**（例: ファイル < toml で toml が勝つ、などルールを固定）し、**1 つの「スロット用レイヤー」**（`.envrc.slot` の中身＝`export KEY=val` の列、または `.env.local` 形式）に **書き出す**。
- **その後の読み方は案 A/C と同じ**: プロジェクトの `.envrc` が **先に `dotenv` で .env**、**続けて生成ファイルを読む**。F は **「生成物の中身をどう組み立てるか」**が C（toml のみ）や D（ファイルのみ）より柔らかい **中身の合成ロジック**の違いであり、**direnv への届け方自体は A/C と同型**である。

### 7.6 案 G

- アプリが `.env.slot` を明示的に読むため、**プロジェクトがスロット慣習に依存する**。要件として不採用とする想定。

## 8. 子シェル案（オプション）とスロット切り替え

### 8.1 方針

- **gwq の `gwq cd` と同様、子シェル起動はデフォルトではなくオプション**とする想定。
- **子シェル専用の env**（通常の Load やフックの子プロセスには載せない値）は **設定で分離**できるようにする（例: `[shell]` 配下や `[[slots]] shell_env` など。詳細は設計時に決定）。

### 8.2 「スロットシェル内で再度 `git slot` したとき」の制約

- ユーザーが **通常どおり** `git slot shell <別スロット>` を実行すると、**現在のシェルが親**で **git-slot が子プロセス**として起動する。git-slot がその子としてさらにシェルを起動すると **ネスト**する。
- **子プロセスである git-slot は、親シェルに `exit` を送れない**（親のプロセスを置き換えられない）。したがって「自動で exit してから親で git slot をやり直す」を **git-slot 単体で完結させることはできない**。

### 8.3 ネストせずにスロットを切り替える方法

- **現在のシェルプロセスを git-slot に置き換え、その先で新しいスロット用シェルに置き換える**必要がある。シェル上では **`exec`** がそれに相当する。

```text
# スロットシェル内で別スロットへ切り替え（ネストしない）
exec git slot shell <別スロット名>
```

- 流れ: いまの zsh/bash が **プロセスごと** `git-slot` に置き換わり、`git-slot` が **さらに `exec` で** 新しいシェルを起動する実装にすると、**親はもともとの外側のシェル（ターミナル直下）のまま**、中間の「古いスロットシェル」は残らない。

### 8.4 UX 上の補助

- **検出**: 子シェル起動時に `GSL_SHELL_SESSION=1`（仮）などを export しておく。
- **スロットシェル内で `git slot shell` を exec なしで実行した場合**: 警告を出す（例: 「ネストします。切り替えは `exec git slot shell <name>` を使ってください」）。または **非対話では exit code 1** など。
- **任意**: ドキュメントまたは `git slot shell --help` に **`exec` の推奨**を明記。進んだ例として **`alias gsl='exec git slot shell'`** のようなシェル側ラッパーを案内する。

### 8.5 まとめ

| やりたいこと | 現実的な手段 |
|--------------|--------------|
| 子シェルはオプション | フラグまたはサブコマンド（例: `git slot shell`）で gwq と同様に提供 |
| 子シェル専用 env | 設定で通常 env と分離 |
| スロット切り替えでネストしない | **`exec git slot shell <name>`**（シェルが協力する必要あり） |

## 9. ステータス

- **実装済み**。採用した設計: 子シェル方式（案 E の発展形）。
  - `git slot shell [slot]` サブコマンドで子シェルを起動
  - `launch_shell = true` 設定で `set` / TUI も子シェル化
  - スロット用 env は `git-slot.toml` の `[[slots]] env` で定義
  - GSL_* 環境変数 + ユーザー定義 env を子シェルの環境に注入
  - ネスト防止: `GSL_SHELL_SESSION` で検出、同スロット内の switch は許可
  - `--no-shell` フラグでスクリプト用途に対応
